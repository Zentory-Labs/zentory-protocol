# CRITICAL (2)

## 1. totalAssets() clamps to 0 when accrued fees exceed gross value, letting the next 1-wei depositor capture the whole vault
- **Area:** Vaults (ERC-4626, fees, NAV)  
- **Location:** `zentory-protocol/contracts/src/vaults/SpotVault.sol:150`  
- **Category:** share-inflation / total depositor loss  
- **Owner:** engineering  |  **Verdict:** `confirmed`  |  🚫 **BLOCKS MAINNET**

**Impact**

`totalAssets()` returns `gross > performanceFeeAccrued ? gross - performanceFeeAccrued : 0`. Because performanceFeeAccrued only ever increases (finding 1) and `grossValue()` is denominated in the underlying — so it FALLS when the underlying rallies while the vault sits in cash — the clamp is reachable with no attacker action, purely from repeated keeper evaluateFees() calls plus an adverse move. Once totalAssets()==0: every existing holder's previewRedeem returns 0 (their shares are worthless while the tokens are still in the contract), and OZ's `assets.mulDiv(totalSupply + 10**offset, totalAssets + 1)` means a deposit of 100 wei mints ~100x(supply+1e6) shares. With a 1-WBTC seed (supply ~1e14) an attacker paying ~100 wei owns >99% of supply, then redeems the entire vault as soon as gross recovers above accrued. Every real depositor loses 100% of principal to a ~dust attacker. The `_decimalsOffset()==6` mitigation only protects the empty-vault case; it does nothing once totalAssets is pinned to 0 with supply outstanding.

**Recommendation**

Never let totalAssets() silently floor at 0: cap accrual at accrual time (`fee = Math.min(fee, gross - 1)`) and make totalAssets() revert or the vault auto-halt if `performanceFeeAccrued >= grossValue()`. Additionally (a) block deposits/mints whenever `totalSupply() > 0 && totalAssets() == 0`, (b) permanently lock the seed shares (mint the first deposit to address(0) or the treasury and never redeem it) so supply>0 always implies assets>0, (c) add an invariant fuzz test `totalSupply()>0 => totalAssets()>0` and a per-share-value-monotonicity test across deposit/withdraw. Note BaseVault.sol:158 has the mirror-image bug shape (`balanceOf - performanceFeeAccrued` unchecked) which bricks totalAssets() on underflow instead — apply the same guard there.

## 2. applyPayout() can be re-run on the same signalId without limit — repeatable slash or unlimited reward mint
- **Area:** Signals & Epoch Scoring  
- **Location:** `zentory-protocol/contracts/src/signals/EpochScoring.sol:408`  
- **Category:** replay / missing idempotency on payout  
- **Owner:** engineering  |  **Verdict:** `confirmed`  |  🚫 **BLOCKS MAINNET**

**Impact**

applyPayout(signalId) reads accuracyCache[signalId], calls zentStaking.slash()/reward(), emits an event — and records NOTHING. There is no paid/settled flag on the signal, no check that the signal's epoch is settled, no clearing of accuracyCache, and SignalRegistry's Resolved status is never consulted. Any EPOCH_SETTLER holder (a single hot keeper key, in a repo whose deployer/admin key was already leaked in chat) can loop applyPayout on one signalId: each iteration slashes 1.7% of a target provider's staked ZENT, so ~250 calls in a couple of txs zeroes a quant's entire bond; pointed the other way it repeatedly calls zentStaking.reward() at up to 5% of stake per call, draining the reward pool / minting to a colluding address. A buggy keeper retry loop (their known failure mode) does the destructive version by accident. Real staked user ZENT is lost with a fully valid-looking on-chain trail.

**Recommendation**

Add `mapping(bytes32 => bool) payoutApplied` and revert `PayoutAlreadyApplied(signalId)` on re-entry; require `epochStates[signalEpoch].settled == true` and that the signal's epoch matches the settled epoch; delete accuracyCache[signalId] after use; flip the signal to SignalStatus.Resolved (or Slashed) in SignalRegistry inside the same call so registry and scorer cannot disagree. Add a per-epoch aggregate cap on total slashed and total rewarded, checked before any external call, so no key can exceed one epoch's economic budget regardless of call count.

Fix as recommended: a `payoutApplied` mapping is the minimum; the per-epoch aggregate slash/reward budget checked before any external call is what actually bounds the blast radius regardless of call count.

# HIGH (28)

## 3. SpotVault accrues performance fees into a one-way sink: no claimFees(), no setFeeRecipient()
- **Area:** Vaults (ERC-4626, fees, NAV)  
- **Location:** `zentory-protocol/contracts/src/vaults/SpotVault.sol:236`  
- **Category:** fee-accounting / irrecoverable value loss  
- **Owner:** engineering  |  **Verdict:** `confirmed`  |  🚫 **BLOCKS MAINNET**

**Impact**

`evaluateFees()` does `performanceFeeAccrued += fee` and `totalAssets()` permanently subtracts it, but SpotVault has NO claimFees() and NO setFeeRecipient() (grep confirms both exist only in BaseVault). The accrued underlying is therefore unreachable by BOTH sides forever: depositors can never withdraw it (it is netted out of NAV, so every redeem prices it at zero) and the treasury can never collect it (feeRecipient is stored at construction and never read by any function). With 20% perf fee on a live vault this silently vaporises 20% of every alpha leg — e.g. a vault that earns 10% gross permanently destroys ~2% of TVL per HWM step. This is the concrete root cause of the known 'fees do NOT converge on the treasury' gate, and it is exactly the silent-irrecoverable-loss class from the recorder incident: one keeper tx and the value is gone with no retry path, no event a human watches, and no owner.

**Recommendation**

Before any mainnet deposit: (1) add `claimFees()` to SpotVault mirroring BaseVault (nonReentrant, emits a ClaimedFees event, routes to IFeeDistributor when feeRecipient.code.length>0); (2) add `setFeeRecipient(address)` under DEFAULT_ADMIN_ROLE with an event; (3) add an admin `sweepAccruedFeeToVault()` escape hatch so a stuck accrual can be returned to depositors instead of stranded; (4) add a keeper/monitor assertion that `performanceFeeAccrued` returns to 0 within N epochs of each accrual and pages a named on-call human if it does not; (5) add a unit test asserting `sum(redeem all shares) + claimed fees == gross value` so a missing claim path fails CI.

## 4. Stale-price window lets a redeemer or depositor extract the mispricing from remaining depositors (staleness 3600s vs 4H push cadence)
- **Area:** Vaults (ERC-4626, fees, NAV)  
- **Location:** `zentory-protocol/contracts/src/vaults/SpotVault.sol:122`  
- **Category:** oracle manipulation / NAV arbitrage  
- **Owner:** engineering  |  **Verdict:** `confirmed`  |  🚫 **BLOCKS MAINNET**

**Impact**

NAV values the cash leg through `cashToAsset()` at whatever `latestRoundData()` last reported, and the only guard is `block.timestamp - updatedAt > maxOracleStaleness`. DeploySpotVault.s.sol:54 defaults MAX_ORACLE_STALENESS to 3600 while the feed it is wired to (ShadowPriceOracle, pushed by the keeper bot) updates every 4H per its own docstring and DeploySpotVault.s.sol:87 — so operators must widen staleness to >=4H just to keep the vault usable, opening a 4-hour window in which NAV is priced off a stale price. Inside that window there is always a profitable side: if the oracle price is BELOW market the cash leg is overvalued in underlying terms, NAV is overstated, and a redeemer whose payout is covered by the vault's existing underlying balance takes out more WBTC than their shares are worth (no swap occurs, so neither `maxSlippageBps` nor the adapter's minOut guards this path); if the oracle is ABOVE market, NAV is understated and a depositor mints extra shares cheaply and dilutes everyone. At a 50/50 target weight a 5% intra-window move is a ~2.5% risk-free extraction per round trip, paid by the depositors who stay. There is no deviation-vs-previous-round check, no min/max sanity band, and no TWAP.

**Recommendation**

Decouple the two: keep a tight staleness bound AND make the feed's heartbeat shorter than it (push at least every 15–30 min, or use a real push feed). Add to `_oraclePrice()` a max-deviation-from-previous-round check that halts the vault instead of transacting, and value the cash leg with the conservative side of a (spot, TWAP) pair so mispricing can never favour the entry/exit. Charge an exit fee >= expected staleness drift (retained by the vault, not the treasury) so round-tripping is unprofitable, and add an on-chain `lastRebalanceAt`-style freshness assertion in previewRedeem. Add a fuzz test that moves the oracle vs a simulated market price and asserts NAV-per-share for holders never decreases across any deposit or redeem.

## 6. Performance fee has no per-depositor high-water-mark equalization: late depositors are retroactively taxed, timing-aware holders pay zero
- **Area:** Vaults (ERC-4626, fees, NAV)  
- **Location:** `zentory-protocol/contracts/src/vaults/BaseVault.sol:193`  
- **Category:** performance fee math / unfair dilution  
- **Owner:** engineering  |  **Verdict:** `confirmed`  |  🚫 **BLOCKS MAINNET**

**Impact**

Both vaults compute `fee = (nav - highWaterMark) * totalSupply() * performanceFee / (shareUnit * 10000)` (BaseVault.sol:193, SpotVault.sol:234) against the CURRENT total supply, with a single global HWM. Anyone who deposits between two `evaluateFees()` calls is charged 20% of alpha earned before they arrived: deposit at NAV 1.50 with HWM still at 1.00 and the next keeper call removes 0.10 of NAV per share — an instant ~6.7% loss of principal for a depositor who earned none of that gain. The gap scales with how long the keeper has been silent, so the same keeper-goes-quiet failure that froze the track record here converts directly into depositor losses, with no on-chain signal to a depositor that they are about to be taxed. The inverse is worse for revenue: `evaluateFees()` is a discrete, predictable (4H cadence) keeper tx and exit is free, so a sophisticated holder redeems just before it and re-deposits after, paying ~0 performance fee while retail pays the full 20%. Net effect: retail subsidises whales and protocol revenue leaks.

**Recommendation**

Move to standard per-share fee equalization: either (a) accrue the fee continuously and take it as a share dilution (mint fee shares to feeRecipient) so it always applies only to gains accrued while shares were outstanding, or (b) track a per-account entry HWM / series accounting so each holder is charged only on their own alpha. In the interim, snapshot the HWM at each deposit and charge fees only on supply outstanding since the last evaluation, make `evaluateFees()` permissionless and called in the same tx as every deposit/withdraw so the HWM is never stale, and add an exit fee so timing the keeper is not free. Add tests: deposit-immediately-before-evaluateFees must not reduce the new depositor's share value, and withdraw-then-redeposit-around-evaluateFees must not reduce fees paid.

## 9. O(n^2) bubble sort plus ~10 external calls per signal over an attacker-growable epoch list permanently bricks settlement with no escape hatch
- **Area:** Signals & Epoch Scoring  
- **Location:** `zentory-protocol/contracts/src/signals/EpochScoring.sol:583`  
- **Category:** gas DoS / unrecoverable state  
- **Owner:** engineering  |  **Verdict:** `confirmed`  |  🚫 **BLOCKS MAINNET**

**Impact**

settleEpoch iterates epochSignalIds[epochId] three times (stake sum at 268, _scoreProvider at 290 — each doing getEpochSignalProvider + getProviderStake + 5x getStakeAtEpoch + getEpochSignalReturn), then _rankResults runs a memory bubble sort at O(n^2) with full struct copies. ## 14. totalVeSupply never decays and never decrements on withdraw — quorum ratchets up forever, permanently bricking governance

## 32. settleEpoch() is public with no EPOCH_DURATION check — the duration gate lives only in performUpkeep(), so epochs can be fast-forwarded and epochReward paid repeatedly
